# Cartograph：dadm 性能实测

测试时间：2026-11-23 22:33–22:41（北京时间）。采样复核：2026-11-24。

## 结论

本轮确认了打开地图时的额外开销，以及关闭地图后开销的下降。没有完成用户所述“大存档中，站着不动也频繁卡一下”的同规模复现，不能据此宣布性能问题已经解决，也不能据此认定必须拆为伴随进程。

优先处理现有进程中的绘图计算、缓存分配和地图开启时的持续采样。伴随进程仍是可评估的选项：由 MC 管理启动和退出，进入世界自动工作；本轮没有实现或启动此类地图进程。

## 测试对象与条件

- 产品提交：`6cab7901962cad1a9826218e129348c6dd6a75e4`。
- 产品 JAR SHA-256：`3613e9ee8ece506436b3c8ac752b3b0d745dde74479078623e32a33a4d84aca0`，与此前部署版本一致。
- NeoForge 1.21.1；完整测试整合包原有 48 个 JAR，另加 1 个仅用于测量的 QA 模组。QA 不进入正式产品构建。
- dadm：i5-4300U，2 核 / 4 逻辑处理器，8 GB，SSD；JDK 21.0.13。
- OpenGL 使用 llvmpipe CPU 软件渲染，1280×720，渲染距离 5，模拟距离 4，堆上限 2 GiB；JVM ActiveProcessorCount=2。
- 独立复制 UnificationSmoke 世界（22 个 MCA 文件）；该存档为原版世界生成，包含整合包内容，不是用户的实际游玩存档。地图缓存峰值只有 270 块，远小于用户大存档的约 26 万块。
- 仅启动一个测试 MC 客户端。测试结束后客户端正常退出；其进程组为空，私有 Xvfb 已退出。没有修改源整合包实例或个人机器上的整合包。

## 方法与测量边界

依次测试 10 阶段：预热、静止对照、后台采集、移动对照、移动采集、近景、远景、手绘远景、关闭地图后静止、末段静止对照。预热 20 秒，其余每段约 25 秒。

“对照”通过关闭 Cartograph 后端并阻止本世界自动重新打开来暂停实际采集/请求；模组仍被加载，事件监听和部分轻量客户端检查仍存在。它不是卸载模组的整包对照。

移动采用观察者模式，在已预热的 48 格路线往返，每 5 个客户端 tick 更新位置。没有验证长距离新地形探索。每个开图阶段都会重新打开地图，因此远景/手绘结果包含重新打开后的校验与绘图，不代表只在同一屏幕连续缩放或切换风格。

帧时间为相邻 RenderFrameEvent.Pre 的间隔，包含世界绘制、地图绘制、等待、GC 和调度。客户端/服务端 tick 是对应 Pre→Post 事件区间，不能把客户端 tick 当成完整帧时间。结果是单轮观察，阶段顺序和持续预热会影响比较；前段对照比后段更慢，不表示开启 Cartograph 会提升性能。

## 测量结果

p95 / p99 表示 95% / 99% 样本不超过的时间；单位均为毫秒，越低越好。GC 最大暂停来自该 JVM 的统一 GC 日志。

| 场景 | 帧间隔 p95 / p99 | 客户端 tick p95 | 服务端 tick p95 | GC 最大暂停 |
|---|---:|---:|---:|---:|
| 预热（后端暂停） | 363.83 / 614.69 | 17.84 | 104.42 | 153.68 |
| 静止对照（前段） | 188.97 / 246.05 | 9.62 | 61.66 | 78.87 |
| 静止后台采集 | 125.04 / 157.92 | 5.51 | 34.03 | 88.07 |
| 移动对照 | 145.83 / 187.25 | 6.59 | 45.03 | 84.21 |
| 移动后台采集 | 130.75 / 155.07 | 5.22 | 39.60 | 60.62 |
| 打开近景地图 | 237.56 / 306.58 | 12.52 | 51.46 | 72.82 |
| 打开远景地图 | 140.56 / 170.96 | 4.96 | 31.93 | 56.28 |
| 打开手绘远景 | 211.92 / 250.97 | 9.36 | 48.36 | 53.85 |
| 关闭地图后静止 | 115.49 / 146.16 | 4.10 | 32.18 | 53.23 |
| 静止对照（末段） | 131.77 / 151.53 | 4.00 | 38.87 | 53.52 |

近景阶段缓存由 104 增至 270；客户端待处理峰值 128，服务端排队峰值 126，并行请求峰值 8。近景首次开图的填充工作明显多于随后阶段。

关闭地图阶段：视图监听人数峰值 0，客户端/服务端待处理与并行请求峰值均为 0；主线程中含 Cartograph 的采样为 1/230，服务端为 0/141。末段暂停后端的对照为主线程 0/217、服务端 0/132。这支持“当前小存档下，关闭地图后的额外开销较小”，不外推到大存档。

## 采样发现

1. **绘图和界面工作仍占用 MC 主线程。** 近景主线程 276 个样本中 37 个含 Cartograph；手绘远景 269 个中 23 个。手绘调用链包括 `InGameMapTiles.updateAtlas → paint → MapPresentationRenderer.renderPixels → HandDrawnMapData.from`，同时出现 `SatelliteSurfaceRenderer` 的外观和颜色处理。近景还出现 `MapClientCache.keysInBounds`、文字、图标与界面绘制。采样比例不等同于精确 CPU 时间比例。
2. **地图打开时仍有持续采样。** 近景服务端 171 个样本中 21 个含 Cartograph；远景 141 个中 15 个；手绘 164 个中 10 个。主要包括 `LoadedSurfaceReader`、`LiveSurfaceUpdates` 和请求完成处理。关闭地图后的相应额外工作大幅减少。
3. **缓存和绘制存在分配压力。** 开图各阶段，`RegionNbtReader.readChunk` 的分配采样权重约 50–55 MiB / 25 秒；近景还出现 `PersistentRenderedAtlasStore.save` 约 27.8 MiB。界面的 `MapGraphics.fill/icon/renderOutline/drawString` 也反复出现。分配权重是采样估算，不能作为精确分配总量，也不能据此把每次 GC 全归因给地图。
4. **有卡顿来源并非地图。** 软件渲染的 OpenGL 提交在主线程采样中频繁出现；服务端反复出现 Sable / Rapier 物理与原版区块 tick。暂停地图后端时仍出现约 54–84 ms 的 GC 暂停。这些开销在本次完整包对照里仍存在；本轮没有修改这些模组。
5. **主线程同步磁盘阻塞没有成为本轮观测到的热点。** 测量阶段没有记录到主线程/服务端的 JFR 慢文件读写或 monitor 阻塞事件。此结论受 JFR 阈值与采样窗口限制，不能理解为完全没有 I/O 或锁等待。

现有 `disk_reads` 和 `loaded_reads` 只统计成功读取路径，不覆盖所有负查询、live refresh 和重新校验。因此远景计数为 0 时，JFR 仍能看到 MCA 解析分配和已加载区块采样，不能把计数 0 解释为“完全没有地图工作”。

## 对伴随进程方案的判断

当前最明确的可优化点是：减少不变视图的索引遍历与界面分配，复用手绘推导结果，检查已知空块的重复查询，以及把可脱离 Minecraft 对象的像素计算放到受限工作线程。MC 世界读取与 GPU 纹理上传仍需要在各自允许的线程完成，拆进程不会自动消除这些工作。

先用上述具体改动做相同场景的前后对比，再决定是否值得增加 IPC、快照复制、第二套内存和进程生命周期管理。若后续证据表明地图的独立计算或 GC 隔离收益足够，再评估由 MC 自动管理的伴随进程。

## 复核与复现

- 原始指标：`docs/performance/dadm-20261123-metrics.json`。
- 精简采样：`docs/performance/dadm-20261123-profile.json`。
- 测试启动器：`scripts/measure-v31.py`；QA 构建入口：`scripts/measure-v31.gradle`。
- JFR 流式分析：`scripts/analyze-v31-measurement.py` 和 `scripts/JfrPhaseEvents.java`。

QA 构建在 `v3.1/neoforge-1.21.1` 下执行：
```sh
JAVA_HOME=/home/wanstu/sdk/jdk/21 ./gradlew --offline --no-daemon -I ../../scripts/measure-v31.gradle measurementProbeJar
```

启动器以 `prepare` 复制指定源实例，随后 `run` 使用产品 JAR 和独立 QA JAR。参数详见 `python3 scripts/measure-v31.py --help`；禁止将 QA JAR 放入个人实际游玩实例。

分析命令在仓库根目录执行：
```sh
python3 scripts/analyze-v31-measurement.py --lab build/performance-lab --java /home/wanstu/sdk/jdk/21/bin/java
```

本机录制的 JFR 时间基准与统一 GC 日志有漂移。分析器使用 107 个相同 young-GC ID 的开始时间作分段校准，JFR→墙钟比例约 0.76143；GC 暂停直接读取 `gc.log`。校准后各阶段 GC 合计与探针 MXBean 毫秒计数吻合。线程名在 JFR 第一段记录中为 `main`，而游戏日志显示为 Render thread，分析器同时识别两种名称。

原始指标中的 `cores=2` 是 JVM 可用处理器数，不是 dadm 的物理核数说明；旧字段 `process_cpu_percent_all_cores` 实际按此 JVM 数量归一化，不能当作整机占用百分比。报告未用该字段作性能结论。测量工具后续输出已改为 schema_version=2，分别记录 CPU 核心当量与按 JVM 可用处理器归一化的百分比；本轮原始指标保持原样，便于追溯。
