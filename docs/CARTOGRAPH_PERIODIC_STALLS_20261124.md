# Cartograph 周期卡顿：开发 Web 服务空转的定位与处理

日期：2026-11-24（UTC+8）。承接 [未开地图时的后台调查](CARTOGRAPH_IDLE_PERFORMANCE_20261124.md)。本轮测量工具源码提交为 `0f433c3dabb7d10fda6717b9c6ae8edb98b0f9f0`；Cartograph 运行源码仍为 `9ab5552c858eabcae35adae799412f6402b25c58`。

## 结论

找到并处理了一项主要残余负载：当前整合包中 KubeJS 的开发 Web 服务使用 `tiny-java-server 1.0.0-build.33`，在没有等待机制的循环里反复调用非阻塞 `accept`。这会持续占用 CPU 并产生分配；不是地图图像绘制工作。个人实例的同一线程累计 CPU 1,574.22 秒、运行 1,664.06 秒，约相当于持续占用 94.6% 的一个逻辑核。

在 dadm 同一次游戏内保留 8,192 块地图缓存、关闭地图界面、持续采集，只反复停开这个开发 Web 服务：三个开启段的帧 p95 为 65.73—82.63 ms，三个关闭段为 49.19—54.17 ms。各状态约 135 秒内，超过 100 ms 的帧合计为 35→15。开启后的开销会重新出现，改善不能只用一次冷启动后的自然预热解释。

已将个人实例 `kubejs/config/web_server.json` 的 `enabled` 从 `true` 改为 `false`，原文件已备份；**重启 MC 后生效**。这个选项控制开发网页服务；测试中 KubeJS 脚本、统一配方内容和 Cartograph 采集均继续工作。

仍有少量长帧。该结论不等于整合包零卡顿，也不将所有 GC、物理和渲染负载归因于这个服务。

## 已安装代码与个人实例证据

- KubeJS：`kubejs-neoforge-2101.7.2-build.381.jar`；内嵌 `META-INF/jarjar/tiny-java-server-1.0.0-build.33.jar`。两者指纹保存在已安装代码证据中。
- 对实际 JAR 执行 `javap -c -p`：`HTTPServer.start` 调用 `configureBlocking(false)`；`run` 循环调用 `acceptClient`、遍历连接后直接跳回，没有空闲等待；`acceptClient` 在没有连接时直接返回。这里只描述已安装的 build.33，不外推其他版本。
- dadm 线程转储和 JFR 均指向 `sun.nio.ch.Net.accept → ServerSocketChannelImpl.accept → HTTPServer.acceptClient → HTTPServer.run`。
- 个人实例在 19:38 的只读线程转储也命中同一调用链，线程名为 `KubeJS 2101.7.2-build.381`。观察的是已经运行的 MC；实机测试客户端均在 dadm。没有在个人电脑启动第二个游戏或停止正在玩的游戏。
- Web 服务在线程级分配和 CPU 证据中独立可见，不能把“线程名含 KubeJS”直接当成脚本逻辑很重；此处已定位到具体的 Web 接收循环。

## 第一轮：同一进程切换 Cartograph 采集

沿用真实 GeoWorld 存档副本与现有整合包，在同一位置预热 180 秒，再执行八个约 60 秒的采集开关段。地图界面在有效段保持关闭。以下全部保留，没有只挑较好的后段。

| 阶段 | 采集 | 帧 p95 / p99 ms | >100 ms 帧数 | KubeJS Web 线程 CPU 秒 | 实际成功读盘 |
| --- | --- | ---: | ---: | ---: | ---: |
| control_1 | 关 | 102.08 / 133.98 | 59 | 35.77 | 0 |
| mapping_1 | 开 | 86.06 / 131.14 | 36 | 39.62 | 110 |
| mapping_2 | 开 | 73.11 / 116.82 | 22 | 41.00 | 105 |
| control_2 | 关 | 66.10 / 97.38 | 12 | 41.02 | 0 |
| mapping_3 | 开 | 76.47 / 105.14 | 18 | 40.01 | 120 |
| control_3 | 关 | 64.87 / 89.21 | 9 | 41.68 | 0 |
| control_4 | 关 | 62.40 / 85.84 | 11 | 40.07 | 0 |
| mapping_4 | 开 | 72.59 / 102.07 | 15 | 40.25 | 120 |

暂停 Cartograph 后依然有大量长帧，Web 接收线程仍每分钟消耗约 36—41 秒 CPU。相邻 `mapping_1` 中 Cartograph 四个命名后台线程合计约 1.20 秒 CPU；主线程 JFR 中 Cartograph 样本也很少。这支持继续寻找整包中的其他负载，不证明地图所有路径完全没有开销。

这一轮仍存在逐渐预热的趋势，重新开启后端还会触发后台索引扫描，因此不把采集开关段的全部帧时间差解释为地图因果收益。预热中曾通过共享 M 键打开已有地图界面，正式段前关闭；`control_4` 中有一次只读线程转储，命令执行窗口约 1.35 秒，其数据照常保留。第二轮直接调用 Cartograph 前端，且有效段没有截图或线程转储。

## 第二轮：只切换开发 Web 服务

使用独立副本启动；启动配置先关闭开发 Web 服务。QA 打开 Cartograph、从真实现有事实中恢复缓存，45 秒后关图；180 秒预热结束后执行六个约 45 秒的段。顺序为开、关、关、开、关、开。QA 仅在此副本调用 `LocalWebServer.instance().server()` 的公开 `start/stop` 方法。Cartograph 后端在全部有效段连续开启，没有重新扫描的开关干扰。

每个有效段都验证：地图缓存峰值 8,192、界面已关闭、世界绘制正常、实际地表读盘发生、Web 状态符合设定、失焦帧数为 0。测试使用 Intel HD 4400、1280×720、渲染距离 5、模拟距离 4、2 GiB 堆和 2 个 JVM 可用处理器；56 个原有模组继续加载，另加独立测量模组。个人电脑的具体帧时间不等于此旧笔记本。

| 阶段 | Web 服务 | 帧 p95 / p99 ms | 服务端 tick p95 ms | >100 ms 帧数 | Web 线程 CPU 秒 / 分配 MB | 实际成功读盘 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| web_on_1 | 开 | 82.63 / 101.75 | 78.07 | 12 | 29.09 / 534.4 | 62 |
| web_off_1 | 关 | 54.17 / 83.20 | 53.39 | 8 | 0.00 / 0.0 | 64 |
| web_off_2 | 关 | 53.29 / 68.38 | 54.35 | 4 | 0.00 / 0.0 | 59 |
| web_on_2 | 开 | 72.28 / 102.08 | 71.41 | 13 | 29.27 / 504.3 | 61 |
| web_off_3 | 关 | 49.19 / 63.00 | 47.60 | 3 | 0.00 / 0.0 | 66 |
| web_on_3 | 开 | 65.73 / 97.04 | 76.02 | 10 | 30.09 / 505.4 | 89 |

三段各自 p95 的中位数为 72.28→53.29 ms（约下降 26.3%），各自 p99 的中位数为 101.75→68.38 ms（约下降 32.8%）。这是“分段分位数的中位数”，不是把所有帧合并后重新计算的分位数。两种状态的有效总时长分别约 135.05 秒、135.05 秒；超过 100 ms 的帧数为 35→15。

开启时，该线程每 45 秒消耗约 29—30 秒 CPU、分配约 504—534 MB；关闭段没有该线程的活动。线程 CPU 与分配来自 JVM 线程计数；JFR 栈样本比例只用于定位，不当成精确 CPU 占比。线程退出后未出现在期末快照中的少量交界工作也不会计入，因此不把表中 0 理解为所有切换成本严格为零。

实际成功读盘数不同，正常保存、后台进度和游戏负载仍会波动。测试是一个世界、一个固定位置、一个硬件环境中的重复切换，不能覆盖所有探索、战斗或跨维度场景。

## GC 与剩余长帧

用相邻渲染帧的实际时间记录长帧，再与统一 GC 日志的时间区间求交；JFR 时间使用匹配 GC ID 分段校准。代码对已知重叠区间作了定值校验。GC 重叠表示时间上相交，不单凭相交判定完整因果。

| web_off_1 | 261.02 / 118.35 | 3 / 8 | 180.83 |
| web_off_2 | 226.43 / 65.27 | 2 / 4 | 116.34 |
