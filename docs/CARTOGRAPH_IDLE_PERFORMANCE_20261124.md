# Cartograph：未开地图时的后台性能调查

日期：2026-11-24。上一轮提交 `8e3c9cf`，产品 JAR 为 `db63c6f8c7cf3f797d481d31ca75019f17c067854954d6340ab8d96672069ec7`。

## 结论

本轮修复了一个真实的服务端热点：后台完成一个任务时，会反复遍历其他维度的全部初始积压。用用户真实主世界的 312,391 个位置键测量，实际完成函数的 p95 从 20.475 ms 降至 0.0027 ms。真实整合包下界静止采集时，包含该完成函数的服务端栈样本从 705 个降为 0；稍后的采集尾段从 504 个降为 0。

**这不是“整体卡顿已经解决”。** 两轮真实世界测试中，整机帧时间有升有降：下界第一段帧 p95 为 69.85→66.97 ms，但 p99 为 116.65→153.46 ms；稍后同维度采集尾段 p95 为 46.40→50.02 ms。不能把函数优化幅度换算成整机帧率，也不能据此宣称消除了用户的周期卡顿。剩余采样主要落在其他游戏负载，且存在 GC 停顿；需要按这些证据继续定位。

## 已确认的代码问题

`GeneratedChunkBackfill.completeAttempt` 在服务端每次完成一个地图后台任务时，遍历共享的 `initialPending` 集合，判断当前维度是否还有初始任务。这个集合同时包含其他维度的积压。当前维度没有初始任务时，会反复走完其他维度的所有键；只有当前维度时，稀疏散列桶的首次查找也不是廉价的计数检查。

此外，完成通知又遍历全部已知事实来统计当前维度数量，并在已经通知完成后继续尝试调度相同通知。这些处理发生在玩家不打开地图时也会工作的后台完成路径上。

修复将待处理集合和已知事实按维度分组。完成一个键只删除当前维度的该键，使用当前集合的 `isEmpty` 判断完成，统计使用当前维度的 `size`。完成通知提前去重，并处理少量任务可能在扫描线程标记扫描完成前就已完成的时序。

这不是停止地图采集。保存真实区块后仍入队，原有并发、读盘预算、指纹校验和持久化路径继续工作；没有引入旧版本实现或修改缓存格式。

## 实际函数的规模基准

从用户存档的 395 份真实 MCA 位置表取得 312,391 个位置键，调用产品的实际 `completeAttempt`，每个场景预热 32 次、测量 256 次。没有读取或生成地形。此处是独立 JVM 中的函数耗时，不能当成 Minecraft 帧时间。

| 待处理状态 | 修复前 p95 | 修复后 p95 |
| --- | ---: | ---: |
| 其他维度积压 4,096 个键 | 0.319 ms | 0.0031 ms |
| 其他维度积压 312,391 个键 | 20.475 ms | 0.0027 ms |
| 当前维度仍有 312,391 个键 | 1.098 ms | 0.0012 ms |

规模测试说明原算法确有随积压量增长的开销；不能据此断言用户先前的每次卡顿都来自这个函数。本轮开始检查时，个人实例没有新版本的运行日志，最近日志仍来自 11 月 23 日。

## 真实世界副本

本轮只读复制当前整合包和 `live-t1`，在 dadm 运行独立副本：

- 世界约 1.99 GB，生成器为 `geoworld:geoworld`，不是之前的超平坦验收世界。
- 当前整合包 56 个模组，保留相同组合，包括已有的其他地图模组；另加独立 QA 模组。
- 包含用户对应世界的 262,046 份原始地图事实缓存。
- 传输归档 1,583,852,998 字节，SHA-256 为 `fb5b955fd2db4d43a237f6794c0949b877cc4e2863c0830a04b508d438780ef8`，接收后校验一致。
- 原始世界保持关闭状态完成快照，测试只写 dadm 的世界副本。两个产品版本使用独立世界副本和同一初始事实缓存。原始事实写入采用临时文件替换，因此测试使用硬链接节省准备时间；世界文件和其他可变数据始终做真实复制，另核对源事实样本内容没有被测试改写。

## 实机测试方法

使用 dadm Intel HD 4400 硬件 GPU、1280×720、渲染距离 5、模拟距离 4、2 GiB 堆、JVM 可用处理器 2。实际个人电脑的配置和帧时间不等于此测试机。

使用固定位置的观察者测试身份，全程不打开 Cartograph 地图，保持世界正常绘制。顺序测试主世界静止采集及暂停采集、下界预热/静止采集/暂停采集/再次采集，最后回到主世界。暂停只关闭 Cartograph 后端，其他模组继续运行。每个有效静止场景 45—90 秒，预热阶段单列。

快照中没有现成 FULL 下界区块。QA 在独立副本里正常进入下界，由 MC 真实生成区块，在下界预热阶段保存这些真实区块，随后让后台读取真实 FULL 存档数据。原世界不生成、不传送、不保存。测试要求下界测量期间主世界仍有超过 25 万个积压键，并验证实际下界地表读取发生，避免测到空队列。

不在有效阶段截图；完成所有计量后才保存画面证据。前后版本使用同一 QA、场景、初始世界及缓存。每次只运行一个 MC，清理该测试拥有的进程组。帧时间来自渲染帧事件间隔，服务端 tick 来自对应 Pre→Post 区间；单轮顺序测试受预热、温度、世界生成和其他模组负载影响。

## 实机结果

旧版下界静止采集阶段，服务端 1,429 个栈样本中 705 个包含 `GeneratedChunkBackfill.completeAttempt`；暂停采集对照中为 1/278。热点集中在遍历、字符串比较和 `anyMatch`。这确认目标路径在真实游戏中确有显著开销；栈样本比例不等于精确 CPU 时间占比。

修复后，下界采集阶段服务端 844 个样本中有 10 个包含任意 Cartograph 方法，完成函数为 0；采集尾段服务端 434 个样本中有 4 个包含 Cartograph，完成函数为 0。主世界尾段该完成函数由 19 个降为 0。这是采样中未再观察到该热点，不代表每次调用耗时为零。

以下完整列出顺序测试的全部阶段；单位为 ms，单元格为“修复前 → 修复后”。预热阶段不用于计算稳定收益。

| 阶段 | 帧 p95 | 帧 p99 | 服务端 tick p95 | GC 最长停顿 |
| --- | ---: | ---: | ---: | ---: |
| 主世界启动预热 / 暂停采集 | 1092.75 → 813.53 | 1265.78 → 1271.35 | 258.99 → 211.87 | 158.77 → 199.15 |
| 主世界首次采集 | 338.75 → 265.21 | 427.94 → 345.64 | 152.39 → 127.44 | 180.51 → 220.89 |
| 主世界暂停采集 | 101.87 → 95.52 | 126.30 → 123.29 | 90.41 → 80.19 | 90.61 → 89.24 |
| 下界生成及保存预热 | 64.37 → 59.07 | 123.33 → 85.35 | 87.27 → 72.27 | 124.71 → 188.20 |
| 下界采集 | 69.85 → 66.97 | 116.65 → 153.46 | 80.69 → 79.67 | 102.55 → 125.54 |
| 下界暂停采集 | 47.60 → 48.60 | 58.20 → 58.52 | 53.81 → 46.63 | 76.44 → 63.30 |
| 下界再次采集 | 46.40 → 50.02 | 56.11 → 66.11 | 52.36 → 68.56 | 89.95 → 69.37 |
| 回主世界预热 | 159.67 → 129.30 | 258.73 → 193.23 | 101.50 → 104.65 | 142.11 → 106.49 |
| 主世界再次采集 | 67.59 → 68.96 | 87.64 → 99.80 | 88.51 → 76.66 | 107.20 → 111.79 |

测试限制与剩余证据：

- 下界首次采集实际成功读盘 138→95 次，尾段为 87→91 次；新生成区块及保存时序会随运行变化。两轮初始快照相同，但不能声称每一次后台工作完全等量。
- 主世界首次进入的 30 秒预热没有消除全部冷启动负载，首次采集与之后暂停阶段的差值混有预热效应，不能直接当作 Cartograph 的全部开销。
- 下界预热阶段包含 QA 要求的完整保存，两轮单次服务端耗时约 19.8/19.5 秒；这是副本测试的强制保存，已单列为预热，不能当成产品正常静止卡顿。
- 修复后下界采集阶段仍有最长 125.54 ms 的 GC 停顿；主线程还记录到一次约 143.70 ms 的 fastutil JAR 读取，调用栈不包含 Cartograph。GC 停顿不能仅凭时间相关性归因于某个模组。
- 剩余服务端采样常见 Sable/Rapier 物理模拟、原版区块 tick 和碰撞；主线程常见地形、生物群系颜色及渲染。分配采样包含 Xaero 的 ConsistentBitArray。它们是继续调查的线索，不能由此宣称某个其他模组存在缺陷。本轮没有改动或移除这些模组，也没有修改 GeoWorld。
- 修复后 Cartograph 在下界采集主线程样本为 6/1,931，尾段为 4/1,300；后台读取线程仍正常工作，采集没有被关闭。真实世界两轮的检查均通过，所有阶段的隐藏世界绘制计数为 0。

本轮证据支持先消除服务端的无界扫描。把地图工作搬到伴随 MC 的进程，仍需 MC 内部交付任务完成结果；若继续在完成回调遍历全部积压，拆进程也不会自动消除此处开销。当前剩余整机卡顿的采样不足以证明外置地图进程可以解决，暂不把它作为已验证的收益。
