# Cartograph V4 — unified geographic engine

Status: architecture contract and standalone foundation prototype. RC3 stays installed until actual client acceptance. V4 starts with an empty database; no legacy data compatibility or migration.

## Non-negotiable contracts
- One geographic dataset per world and dimension; satellite and hand-drawn are rendering policies, not storage types. A style changes presentation only. Preserve existing supported mode/style combinations.
- 2D and 2.5D are camera presets of the same map. Orthographic camera with world-space center, zoom, yaw and elevation angle (30–90 degrees initial proposal), 90 degrees + north-up restores conventional map. Presets do not change data. Depth testing, side faces, terrain picking and object instances are renderer capabilities; no second map UI or world reader.
- Target tilted appearance: stepped terrain, river/water surfaces, simplified upright trees/buildings, map-like silhouettes and labels, fog only outside known coverage. Never infer a building/tree from roof color alone. Objects require observed facts or known structure metadata; uncertain objects are omitted or explicitly approximate. Never load/generate unknown chunks for mapping.
- Preserve precise top surface and ground/relief heights separately; use ground mesh plus objects (avoid double counting canopy/roof). Water surface, depth, validity, material and biome channels remain independent. Exact coordinate queries use L0, not coarse averages.
- No global rebuild on pan, zoom, angle or style. Data changes invalidate only affected leaf, required halo and ancestor cells. Never invalidate session validation on RAM eviction. Reopen uses disk snapshots; only observed dirty data needs refresh, with bounded reconciliation for external changes.

## Data schema and identity
Raw facts: collect fresh observed state, biome, surface/relief heights and unsigned water depth through a V4 collector. Resolve stable registry keys during capture. No legacy facts, rendered atlases, markers or settings are imported; leave existing files untouched. No compatibility reader or migration task.
Feature dictionary: canonical stable material/state key, biome/tint class, semantic class; hash is for lookup, equality for collision checks, integer ID for indexing. No exact height/position in feature identity. Disk IDs scoped to a versioned dictionary/region, never assume runtime registry IDs stable. Prototype uses in-memory IDs only.
Independent channels: observed mask, both height fields and their separate valid counts, linear RGB sums, class histogram, water statistics, future directional edge connectivity and observed object geometry. Coarse cells retain weighted sums and counts, not averages of averages; missing cells are excluded and coverage retained.
Use world-aligned powers-of-two grid, floor division for negative coordinates, parent = floorDiv(child,2). Cross-chunk and cross-region aggregation. Fine-to-coarse levels 0–10 initially; extend only if measured. Unknown partial coverage must remain visibly distinct. Preserve narrow waterways through observed geometry/connectivity overlay later rather than inventing a river from percentages.
Prototype uses sparse objects for correctness, NOT production memory layout; use packed region pages and bounded buffers after measurement.

## Region persistence and scheduling (reference implementation; production optimization pending)
Key: world/dimension/schema/region/LOD; indexed compressed pages, content revision and checksum, durable append transaction, corruption detection, incomplete-tail recovery, separate new V4 directory. Separate factual schema/derivation versions from presentation versions. Measure page sizes and codecs before choosing. Use bounded background IO/derivation, cancellation and coalescing by key/revision, viewport priority with reserved capacity for observed dirty writes. Main thread captures permitted immutable snapshots only; render thread owns GPU upload budget. Cache eviction is not a world change. Read cached coarse pages directly, without loading their descendants. Style/angle changes must not enqueue scans.

## Rendering and interaction (pending)
One renderer, shared world-space coordinate system, orthographic projection, stable anchored zoom, yaw rotation and constrained tilt. Draw terrain mesh with stitched LOD boundaries and valid-mask clipping, top and side surfaces; water separately; simplified observed object instances; world-anchored labels/markers, contours, navigation; depth-aware picking with unknown rejection. At north-up 90 degrees match 2D map coordinates. GPU palette/LUT and per-channel texture sampling, shader effects and CPU fallback if necessary; verify actual game and WebGL support. Same drawing policy and style at any angle. Angle/rotation changes update matrices; new viewport coverage loads only relevant pages. No previous-style flash.
Marker drag fix remains an independent V3.1 branch; do not lose it at integration.

## Gates
A: standalone deterministic aggregation, feature equality and negative coordinates.
B: collect fresh real facts, stable output across restart, exact known coverage, localized edits, bounded storage and memory. Include regions larger than 8192 chunks; no legacy migration.
C: native render prototype with 90-degree parity, 45-degree relief/side faces, 360 yaw, picking round-trip, no scans on style or angle changes. Verify actual GPU support and fallback.
D: object display, water, seams, continuous LOD and marker drag/click. Existing style combinations and UI regression suite.
E: actual DADM modpack acceptance: cold/warm opening, continuous zoom/pan/return, all style and camera transitions, restart, FPS frame-time p50/p95/p99, TPS/MSPT, heap/GC, disk reads, derivation/upload counters. Compare identical world and settings against RC3 and no-map control. No deployment until gates pass. 60 FPS/next-frame warm switch are targets, not measured results.

Implemented reference: 32x32 sparse pages per LOD; local feature palette, weighted statistics, Deflate and CRC32C, single-writer append transaction log, bounded page-count LRU, direct reads at any LOD. Pixel and aligned 16x16 chunk updates rewrite at most one page per level; unchanged cells do not propagate. Production requires multi-chunk batching, packed channels, byte-budgeted caches, explicit world/dimension integration, async queue and power-loss testing. Do not deploy synchronous writes into Minecraft.

Worker reference: one serialized owner per V4 world/dimension, asynchronous open, bounded visible/prefetch read queues, same-key deduplication and priority promotion, obsolete viewport cancellation, bounded chunk write queue with latest full-snapshot coalescing, fair writes after at most four visible reads, graceful drain and explicit commit/superseded/failure receipts. A rejected or failed capture remains dirty; a queued snapshot is not durable. Read results are immutable snapshots, not write barriers; caller uses viewport generation and invalidates affected pages on commit. Completion callbacks must be nonblocking or use their own executor. Page LRU uses count plus estimated byte budget, not a measured JVM heap ceiling; queue entries and external retained results are separate. Preserve unrelated cache pages across successful writes. Actual Minecraft collector, packed storage, cross-chunk batching, integration and profiling remain pending.

## World-wide generation and large-world acceptance (mandatory)
- Every eligible observed/generated chunk must eventually have fresh V4 facts and all LODs, even when the map is never opened. No old Cartograph cache/marker/settings import. The viewport is ONLY a priority hint for page residency/GPU upload; it never gates capture, LOD generation or durable writes. Closing the map cancels optional reads/uploads only, not geographic work.
- Fresh existing-world backfill must enumerate actual generated chunks from Minecraft region files with bounded streaming and independently reconcile loaded/changed chunks. Do not generate unknown chunks, load chunks just for the map, or copy old Cartograph facts. The durable discovery/dirty index is still pending; in-flight capture is bounded, a rejected or failed ticket must remain pending, and only a matching committed revision clears it.
- CapturePump prototype has a cooperative nanosecond budget and hard column/start/in-flight caps, checks source validity per tick and before submission, releases loaded chunk references before awaiting IO, retains snapshots under write backpressure and retries without recapture. It has no viewport dependency. The real Minecraft event/region adapters and shutdown reconciliation are not yet implemented.
- Write batches combine up to 64 aligned chunk snapshots (up to 16 if visible reads wait), merge changes across LOD pages, and read each touched page once per level. Transaction cap 32 MiB and 704 pages; page-count and estimated-byte LRU limits remain in place. Production packed channels, write-back/index layout and bounded durable discovery still need profiling.
- Synthetic EADM measurements (Java heap cap 256 MiB; repeated pseudo-random sample sets, no actual Minecraft IO): 64 chunks single vs batch: 5.075 vs 0.798 s, 704 vs 56 page writes; 1024 batch: 7.369 s, 896 writes, 16 reads, 6154939 bytes; 4096 batch: 24.646 s, 3584 writes, 308 reads, 24609873 bytes. Restart overview reads four pages, exact coverage checked. These are not gameplay performance measurements.
- Acceptance must include >=100k generated chunks and a million-chunk stress case, real save/actual world collection, cold/warm overview, sustained background generation without UI, bounded queues and heap, disk footprint/throughput, no repeated world reads on style/camera changes, render frame p95/p99 and server MSPT/TPS during concurrent movement and generation. Use DADM for real gameplay; do not claim pass based on synthetic storage alone.
## Storage throughput experiment 2
- Fresh V4 format only. Compact L0 stores the feature palette index, exact two heights, depth and linear RGB channels; redundant aggregate counts/histograms are reconstructed losslessly. Deflate BEST_SPEED. No old format reader or migration.
- One append-only transaction log per world/dimension, with CRC32C and commit footer, one force(true) per batch, latest-page offset index, exact revisions and incomplete final frame truncation. Full corrupted frames fail closed. The logical page count is not the number of flushes. Retains single-owner contract; no multi-process writer support.
- Synthetic EADM Java heap cap 256 MiB, same ScaleTest fixture and timer: 4096 chunks / batch 16 = 4.799 s, 853.5 chunks/s; batch 64 = 3.441 s, 1190.3 chunks/s, 1920 page writes, 64 forced flushes, 21,942,287 bytes. 16384 chunks / batch 64 = 14.753 s, 1110.5 chunks/s, 7680 page writes, 256 forced flushes, 88,364,297 bytes. Correct exact coverage, four coarse page reads, no-op update and five independent regression suites.
- Important blocker: this is an experimental backend, not production acceptance. Log keeps obsolete page versions; startup currently scans and checksums the entire log (21.94 MB/14.4 ms for 4096; 88.36 MB/114 ms for 16384 on warm filesystem cache). Need sharded/indexed checkpoints, bounded index residency and log compaction before large-world acceptance. Actual power-loss tests, Minecraft fresh capture and gameplay latency remain unverified. No legacy files touched.
## Storage throughput experiment 3
- Dense page-local scratch arrays with bitset dirty tracking replace per-column coordinate-key hash maps, parent HashSets and repeated child hash lookups. Each aligned 2x2 group resides in one page; recompute only touched groups, respecting negative page coordinates. Page-local direct slot order replaces TreeMap sorting. Leaf validation checks invariants without recreating objects.
- Synthetic EADM Java heap cap 256 MiB, same fixture and batch 64: 4096 chunks = 2.815 s (1455.1 chunks/s); 16384 chunks = 11.568 s (1416.4 chunks/s). Same persisted size and logical writes as experiment 2. Five existing regressions and DensePyramidTest (68003 oracle comparisons across randomized updates, deletions, repeated chunks, negative coordinates and restart) pass.
- This is not a packed primitive-channel production store yet: Entry/Aggregate objects, Map publication, per-page compression, serialized IO and append-log startup scans remain. Profile before further changes; no gameplay performance claim. Need bounded sharded indexes/compaction and larger scale tests.
## Storage throughput experiment 4 — 10k chunks/s target, not yet achieved
- Bulk ByteBuffer numeric encoding/decoding, exact per-LOD unsigned field widths, byte-plane transpose, LZ4 Java safe implementation (existing Minecraft 1.21.1 dependency), cached page weights and bounded two-thread page encoding by default (max four, process-wide). No compatibility or migration for experimental page versions; production dependency/security/packaging review pending.
- Spatially ordered fresh backfill experiment uses up to 256 chunks per transaction. Online worker stays at 16/64 when visible reads are/are not queued. A 1024-chunk trial was not consistently faster and is not retained. No viewport dependency for generation.
- EADM i5-11260H (6C/12T), Java heap cap 256 MiB, synthetic exact L0-L10 persistence, same repeated sample values and changed spatial processing order as noted. Previous baseline 4096: 2.815s /1455.1/s, 21,942,287 bytes; 16384: 11.568s /1416.4/s, 88,364,297 bytes. Intermediate compact row-major LZ4 16384 best 2.775s/5904.9/s; later repeat 3.831s/4277.0/s. Final byte-plane format 4096: 1.086s/3773.2/s, 10,899,905 bytes, 16 durable flushes. Final 16384: 6.320s/2592.5/s, 43,642,255 bytes, 64 durable flushes; repeats 6.703s/2444.1/s (one encoder), 6.927s/2365.4/s (two). Shared machine results vary; no stable 10k claim. Retain byte-plane format as a storage/throughput experiment, not a proven throughput win for all workloads. The 256-chunk batch is not yet integrated into the real-world capture path.
- Seven regression suites passed, including exact maximum unsigned field widths and sums for L1-L10, unknown height, deterministic encoding, truncated compressed payload rejection, and 68003 independent aggregation comparisons. No real Minecraft runtime test.
- Next: profile with a controlled DADM benchmark; packed primitive leaf/aggregate pages and capture snapshots, region-independent aggregation and asynchronous commit pipeline, durable region index/compaction. Test real terrain entropy and 100k/1m chunk scales, game tick/render latency separately. The 10k/s target means complete fresh facts + 11 LODs + durable commit, not cache hits or dropping detail.
## Storage throughput experiment 5 — synthetic 100k target passed
- Immutable slot-indexed page arrays replace internal per-pixel maps; external immutable map view is lazy. Work pages directly clone slots and compare by index. Numeric encoder reuses thread-local bounded scratch and writes final byte planes directly, avoiding intermediate arrays/stream copies. Transaction writer preallocates exact byte length and computes the new offset index while serializing; durable force and recovery checks retained. Packed primitive leaf/aggregate representation and parallel region aggregation are still pending.
- EADM, heap cap 256 MiB, synthetic repeated pseudo-random sample fixture (not game collection), 256-chunk transactions, 2 encoder threads by default. 16,384 chunks: 2.172s/7,543.6 per s (2 threads), 1.699s/9,643.7 per s (4 threads), 1.500s/10,920.6 per s (2 threads). 102,400 chunks repeated three times: 8.390s/12,204.6 per s; 7.584s/13,502.9 per s; 6.764s/15,138.7 per s. Each run 26,214,400 pixels, 11 LODs, 36,800 logical page writes, 400 force(true) commits, 273,012,391 bytes, four coarse page reads after reopen. Log startup scans full 273 MB in 211–237 ms on warm filesystem cache. Exact coverage and unchanged chunk no-op validated. Results vary with shared host load and JIT; the target is met for this synthetic storage workload, not real terrain acquisition or gameplay.
- All seven regression suites pass. Next tests: independently varying terrain samples, one million chunks, actual Minecraft region ingestion and frame/tick latency. Durable bounded region index, compaction and production scheduling remain blockers; no legacy imports and no deployment.
## Storage throughput experiment 6 — 100k/s challenge
- Fresh-only spatial shards of 1024x1024 blocks (64x64 chunks), aligned exactly with L10 boundaries; each L0-L10 cell has one owner, including negative coordinates. Independent shard logs allow bounded regional parallelism. Existing incremental algorithm remains available within each shard. No old data migration or format compatibility.
- FreshRegionBuilder recursively builds L0-L5 pages bottom-up, then the shard's partial L6-L10 pages, each physical page once. Leaf snapshots accept primitive int/char channels with immutable feature references; parent aggregation uses primitive arrays, no per-parent Entry objects. Shared lossless page format and checksums; append transactions forced to disk before staging directory publication. Refuses existing shard and removes failed stage. Directory fsync/power-loss and multi-owner enforcement still need production work.
- EADM i5-11260H, Java heap cap 256 MiB, synthetic 102400 chunks, -XX:ActiveProcessorCount=4 and one encoder per process setting. CPU time is JVM process CPU time including GC/JIT, average logical-core-equivalent = CPU time / wall time (not system-wide usage). Initial incremental shard benchmark 2/4 workers: 7.341/7.186 s, 13949/14249 chunks/s, CPU 22.797/31.359 s. Fresh builder entry-snapshot first iteration 1/2/4 workers: 5.843/4.273/3.747 s, 17526/23964/27325 chunks/s, average cores 1.21/2.30/3.83. Final packed snapshot path with same repeated prebuilt fixture: 6.076/4.076/3.702 s, 16855/25122/27657 chunks/s, CPU 7.703/9.813/15.578 s, avg cores 1.27/2.41/4.21. All 25 shards, 26,214,400 columns, 34,250 logical page writes, 150 forced commits, 271,307,530 bytes; exact reopened coverage. Input snapshots were prebuilt outside timed loop.
- Independently coordinate-seeded synthetic snapshots generated within timed interval, 102400 chunks, 2/4 workers: 4.687/4.209 s, 21848/24331 chunks/s, CPU 10.797/17.453 s, avg cores 2.30/4.15, 306,979,396 bytes; exact reopened coverage and sampled leaf verification. This is stronger synthetic entropy evidence, not Minecraft NBT parsing. Eight independent suites including FreshRegionBuilderTest (2411 exact LOD/leaf comparisons, sparse coverage, negative coordinates, failed stage/no overwrite, incremental reopen) pass.
- 100k/s is NOT met. Fresh path reduces CPU per chunk and eliminates repeated high-LOD writes, but more regional workers show diminishing returns and greater CPU use. 100k/s with current fixture would require ~265-300 MB/s persisted output before write amplification, and lower CPU time per chunk. Next investigate specialized lossless packed channel/bit-width encoding, reuse parent buffers and benchmark stage timings under fixed CPU budget. Global render-page assembly/overview index, durable discovery, region scheduling and log compaction remain pending. Shard benchmark reopens 25 separate coarse pages, not 4 world-global pages. No game integration, deployment, or actual TPS/FPS claim.
