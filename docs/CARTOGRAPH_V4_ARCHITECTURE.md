# Cartograph V4 — unified geographic engine

Status: architecture contract and standalone foundation prototype. RC3 stays installed until actual client acceptance. V4 starts with an empty database; no legacy data compatibility or migration.

## Non-negotiable contracts
- One geographic dataset per world and dimension; satellite and hand-drawn are rendering policies, not storage types. A style changes presentation only. Preserve existing supported mode/style combinations.
- 2D and 2.5D are camera presets of the same map. Orthographic camera with world-space center, zoom, yaw and elevation angle (30–90 degrees initial proposal), 90 degrees + north-up restores conventional map. Presets do not change data. Depth testing, side faces, terrain picking and object instances are renderer capabilities; no second map UI or world reader.
- Target tilted appearance: stepped terrain, river/water surfaces, simplified upright trees/buildings, map-like silhouettes and labels, fog only outside known coverage. Never infer a building/tree from roof color alone. Objects require observed facts or known structure metadata; uncertain objects are omitted or explicitly approximate. Never load/generate unknown chunks for mapping.
- Preserve precise top surface and ground/relief heights separately; use ground mesh plus objects (avoid double counting canopy/roof). Water surface, depth, validity, material and biome channels remain independent. Exact coordinate queries use L0, not coarse averages.
- No global rebuild on pan, zoom, angle or style. Data changes invalidate only affected leaf, required halo and ancestor cells. Never invalidate session validation on RAM eviction. Reopen uses disk snapshots; only observed dirty data needs refresh, with bounded reconciliation for external changes.

## Data schema and identity
Raw facts: collect fresh observed state, biome, surface/relief heights and unsigned water depth through a V4 collector. Resolve stable registry keys during capture. No legacy facts, rendered atlases, markers or settings are imported; leave existing files untouched. No compatibility reader or migration task.
Feature dictionary: canonical stable material/state key, biome/tint class, semantic class; hash is for lookup, equality for collision checks, integer ID for indexing. No exact height/position in feature identity. Disk IDs scoped to a versioned dictionary/region, never assume runtime registry IDs stable. Prototype uses in-memory IDs only.
Independent channels: observed mask, both height fields and their separate valid counts, linear RGB sums, class histogram, water statistics, future directional edge connectivity and observed object geometry. Coarse cells retain weighted sums and counts, not averages of averages; missing cells are excluded and coverage retained.
Use world-aligned powers-of-two grid, floor division for negative coordinates, parent = floorDiv(child,2). Cross-chunk and cross-region aggregation. Fine-to-coarse levels 0–10 initially; extend only if measured. Unknown partial coverage must remain visibly distinct. Preserve narrow waterways through observed geometry/connectivity overlay later rather than inventing a river from percentages.
Prototype uses sparse objects for correctness, NOT production memory layout; use packed region pages and bounded buffers after measurement.

## Region persistence and scheduling (reference implementation; production optimization pending)
Key: world/dimension/schema/region/LOD; indexed compressed pages, content revision and checksum, durable append transaction, corruption detection, incomplete-tail recovery, separate new V4 directory. Separate factual schema/derivation versions from presentation versions. Measure page sizes and codecs before choosing. Use bounded background IO/derivation, cancellation and coalescing by key/revision, viewport priority with reserved capacity for observed dirty writes. Main thread captures permitted immutable snapshots only; render thread owns GPU upload budget. Cache eviction is not a world change. Read cached coarse pages directly, without loading their descendants. Style/angle changes must not enqueue scans.

## Rendering and interaction (pending)
One renderer, shared world-space coordinate system, orthographic projection, stable anchored zoom, yaw rotation and constrained tilt. Draw terrain mesh with stitched LOD boundaries and valid-mask clipping, top and side surfaces; water separately; simplified observed object instances; world-anchored labels/markers, contours, navigation; depth-aware picking with unknown rejection. At north-up 90 degrees match 2D map coordinates. GPU palette/LUT and per-channel texture sampling, shader effects and CPU fallback if necessary; verify actual game and WebGL support. Same drawing policy and style at any angle. Angle/rotation changes update matrices; new viewport coverage loads only relevant pages. No previous-style flash.
Marker drag fix remains an independent V3.1 branch; do not lose it at integration.

## Gates
A: standalone deterministic aggregation, feature equality and negative coordinates.
B: collect fresh real facts, stable output across restart, exact known coverage, localized edits, bounded storage and memory. Include regions larger than 8192 chunks; no legacy migration.
C: native render prototype with 90-degree parity, 45-degree relief/side faces, 360 yaw, picking round-trip, no scans on style or angle changes. Verify actual GPU support and fallback.
D: object display, water, seams, continuous LOD and marker drag/click. Existing style combinations and UI regression suite.
E: actual DADM modpack acceptance: cold/warm opening, continuous zoom/pan/return, all style and camera transitions, restart, FPS frame-time p50/p95/p99, TPS/MSPT, heap/GC, disk reads, derivation/upload counters. Compare identical world and settings against RC3 and no-map control. No deployment until gates pass. 60 FPS/next-frame warm switch are targets, not measured results.

Implemented reference: 32x32 sparse pages per LOD; local feature palette, weighted statistics, Deflate and CRC32C, single-writer append transaction log, bounded page-count LRU, direct reads at any LOD. Pixel and aligned 16x16 chunk updates rewrite at most one page per level; unchanged cells do not propagate. Production requires multi-chunk batching, packed channels, byte-budgeted caches, explicit world/dimension integration, async queue and power-loss testing. Do not deploy synchronous writes into Minecraft.

Worker reference: one serialized owner per V4 world/dimension, asynchronous open, bounded visible/prefetch read queues, same-key deduplication and priority promotion, obsolete viewport cancellation, bounded chunk write queue with latest full-snapshot coalescing, fair writes after at most four visible reads, graceful drain and explicit commit/superseded/failure receipts. A rejected or failed capture remains dirty; a queued snapshot is not durable. Read results are immutable snapshots, not write barriers; caller uses viewport generation and invalidates affected pages on commit. Completion callbacks must be nonblocking or use their own executor. Page LRU uses count plus estimated byte budget, not a measured JVM heap ceiling; queue entries and external retained results are separate. Preserve unrelated cache pages across successful writes. Actual Minecraft collector, packed storage, cross-chunk batching, integration and profiling remain pending.

## World-wide generation and large-world acceptance (mandatory)
- Every eligible observed/generated chunk must eventually have fresh V4 facts and all LODs, even when the map is never opened. No old Cartograph cache/marker/settings import. The viewport is ONLY a priority hint for page residency/GPU upload; it never gates capture, LOD generation or durable writes. Closing the map cancels optional reads/uploads only, not geographic work.
- Fresh existing-world backfill must enumerate actual generated chunks from Minecraft region files with bounded streaming and independently reconcile loaded/changed chunks. Do not generate unknown chunks, load chunks just for the map, or copy old Cartograph facts. The durable discovery/dirty index is still pending; in-flight capture is bounded, a rejected or failed ticket must remain pending, and only a matching committed revision clears it.
- CapturePump prototype has a cooperative nanosecond budget and hard column/start/in-flight caps, checks source validity per tick and before submission, releases loaded chunk references before awaiting IO, retains snapshots under write backpressure and retries without recapture. It has no viewport dependency. The real Minecraft event/region adapters and shutdown reconciliation are not yet implemented.
- Write batches combine up to 64 aligned chunk snapshots (up to 16 if visible reads wait), merge changes across LOD pages, and read each touched page once per level. Transaction cap 32 MiB and 704 pages; page-count and estimated-byte LRU limits remain in place. Production packed channels, write-back/index layout and bounded durable discovery still need profiling.

## Active chunk update policy
- User decision: actual server-side loaded chunks have priority independent of why they are loaded (player, portal, forced ticket, mod chunk loader). Per dimension, lifecycle events feed ActiveChunkScheduler. Do not infer activity from player radius, map viewport or entities ticking. No map-triggered chunk loading.
- Loaded missing/dirty chunks are high priority. Verified clean loaded chunks receive staggered low-frequency review; dirty burst limit ensures due review is not starved. Mutation coalescing, per-chunk retry/capture cooldown, ticket reservation and revision checking, no all-active scan per tick, one scheduled node per active chunk. CapturePump retains hard column/start/outstanding limits and cooperative time budget. Review interval and cooldown are configurable; production defaults require gameplay measurement.
- On unload clean active records are removed. Dirty or unfinished capture/review transfers to saved-world dirty handoff; rejected handoff remains pending, reload inherits unaccepted dirty work, stale receipts cannot clear newer state. An inactive saved/mutation event also enters handoff. Saved-world processing must be independent of the viewport and reconcile saved revisions with live writes, including in-flight writes across unload/reload. Only a committed matching revision clears dirty state; equal geographic snapshots remain no-op writes.
- Current scope: standalone scheduler and CapturePump integration, not wired to actual NeoForge/Fabric lifecycle or mutation hooks. Saved dirty handoff is in-memory until the external receiver accepts it; durable saved-world dirty index, save identity verification, shutdown/restart replay, global budget across dimensions and starvation under continuous mutations need implementation. A receiver must not block the server thread and must own accepted work durably. The scheduler does not force chunks or scan Minecraft data itself.
- Regression covers 100000 coalesced events, distant loaded chunks, bounded work, periodic fairness, retry cooldown, mutation invalidation, unload/reload and stale receipt, rejected saved handoff, no-op clean unload, 50000 active lifecycle records and 100000 idle polls, capture pump integration. No actual gameplay claim. High speed, reliability, stability and low resource overhead take precedence over peak throughput.
## Durable dirty work handoff
- SavedDirtyIndex is a per-dimension, single-IO-owner append journal of pending chunk positions and persisted monotonic tokens. Mark and matching acknowledgements batch up to 256 records, checksum each frame and force before returning. Duplicate marks replace the pending token; stale or duplicate acknowledgements cannot remove newer work. Restart replays marks/acknowledgements, truncates incomplete trailing frames and rejects fully corrupt frames. No geography payload or legacy import.
- DirtyHandoffQueue is bounded by queued plus in-flight count, has no extra internal threads, and provides asynchronous durable receipts. ActiveChunkScheduler rotates bounded inactive candidates fairly and retains each until a matching successful receipt. Queue saturation/failure leaves work pending. New changes and reloads cannot be cleared by old receipt. prepareShutdown moves dirty and reserved active work to the inactive handoff; caller must stop lifecycle intake/capture starts, drain/confirm receipts before teardown, and close input only after transfer. No synchronous disk operation in the tick owner.
- Thirteen standalone regression suites passed, including restart pending/clear, stale durable token, torn append, corrupt frame rejection, bounded queue, retry fairness, unload/reload races, shutdown transfer, late receipt, and batched matching acknowledgements. Tests are isolated from actual Minecraft runtime.
- Limitations: only successfully forced records are durable. Sudden exit before handoff requires saved-world discovery/identity reconciliation; no claim of exactly-once recovery or power-loss directory durability. Saved-data reader/commit arbitration with newer live captures, actual NeoForge lifecycle/stop hooks and shared dimension resource budget remain pending. Journal compaction and bounded on-disk index residency are not implemented; pending map grows with unique dirty positions. No production deployment or old data migration.
